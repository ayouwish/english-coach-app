## Q1 🔴 “录音不出户”与 hybrid 部署冲突

**事实**

- 客户端只把数据传到家庭 NAS（`english.dreamsearch.top/api`）。
- 但仓库 `deploy/.env` 当前为 `PROVIDER_MODE=hybrid`（云为主 + 本地兜底），可能调用 Azure Speech / DeepSeek / 智谱。
- 因此“录音不出户”在当前部署下**不成立**（至少不能作为无条件承诺）。

**选项**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 调整承诺（推荐） | 隐私文案写“上传到家庭 NAS，可能由 NAS 转发给云端语音服务商”；列出类别 | 不改后端；诚实；上架风险低 | 营销卖点弱；家长可能介意 |
| B. 切 local | `PROVIDER_MODE=local` 或分项全 local；关闭云 OCR/LLM/插画 | 真正“不出户” | 需要本地模型/GPU；评分质量/速度可能下降；插画/故事能力受限 |
| C. 混合承诺 | 录音/评测 local，LLM/插画用云；文案逐项说明 | 平衡 | 配置复杂；需后端暴露逐项 provider；仍不是“全部不出户” |

**建议**：先 A，确保 M0 文案不撒谎；如果“不出户”是产品核心卖点，再评估 B（需要硬件/模型/时间）。

**需要谁拍板**：产品/家长（家庭自用即你本人）+ 部署方。
**影响**：隐私文案、上架材料、是否买 GPU/换模型、M2 能力范围。

## Q2 🔴 对话一轮：客户端三步 vs 后端一体化

**事实（代码核对）**

现有 `POST /api/chat/sessions/:id/turn`：

- **要求 `text` 非空**；
- `audio` 只用于后台发音评估；
- 响应**不返回 TTS 音频**。

所以“只有语音输入”的移动端一轮需要：

```text
POST /asr → POST /turn(audio+text) → POST /tts
```

**选项**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 客户端三步（推荐先做） | ChatService 编排 ASR→turn→TTS | 不改后端；可独立上线 | 3 次请求；延迟叠加；任一步失败要分别处理 |
| B. 后端一体化 | `/turn` 内部 ASR + 返回 TTS URL/bytes | 一次请求；体验最好；逻辑集中 | 需改后端契约；错误语义/超时/费用控制要重做 |
| C. 折中 | `/turn` 内部 ASR，但 TTS 仍客户端取 | 少一次请求；TTS 可缓存/复用 | 仍需后端改；收益有限 |

**建议**：M1 用 A 上线；同时把 `ChatService.turnByVoice()` 封装好，B 完成后只换内部实现。若对话是核心体验、且能改后端，优先 B。

**需要谁拍板**：后端负责人 + 产品。
**影响**：M1 工期、对话延迟、错误处理复杂度、后端契约版本。

## Q3 🔴 应用市场 vs 内部签名分发

**背景**

- 服务只在家庭网络可达（公网不可达）；应用市场审核时审核员可能无法访问服务。
- 上架需要隐私政策 URL、软著/备案、隐私检测、儿童应用相关材料（以当期要求为准）。
- 内部签名分发需要设备管理/证书有效期/安装说明。

**选项**

| 方案 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| A. 内部签名（推荐首发） | 家庭/亲友少量设备 | 快；不用审核；可控 | 证书过期需重签；安装门槛；无法公开分发 |
| B. AppGallery | 想公开/长期 | 正规；自动更新 | 审核可能因“服务仅内网”被拒；合规材料多 |
| C. 双轨 | 内部先用，后上架 | 风险低 | 两套发布流程 |

**建议**：先 A 把 M0–M3 用起来；M4 再评估 B。若上架，需要提前准备隐私政策公网页、演示账号/可访问的演示环境（可能需要临时公网映射，另做安全评估）。

**需要谁拍板**：你（发布者）。
**影响**：M4 工期、合规成本、是否需要公网演示环境。

## Q4 🟠 Cookie 会话 vs Bearer Token

**现状**

- 服务端只认 `ec_session` Cookie（httpOnly, sameSite=lax, 30 天）。
- 客户端方案 A：手动 `Cookie` 头 + Asset Store 持久化。
- 客户端方案 B：后端新增 Bearer Token（签发/刷新/吊销），需改后端。

**对比**

| 维度 | A. Cookie（当前） | B. Bearer Token |
|---|---|---|
| 后端改动 | 无 | 新增登录/刷新/吊销端点；双认证中间件 |
| 客户端复杂度 | 手动解析/持久化 Cookie；每请求加头 | 标准 `Authorization`；易测试 |
| 过期/刷新 | 30 天固定；过期重登 | 可短 access + refresh |
| 吊销 | 删 sessions 行；无 logout-all | 可精细吊销 |
| CSRF | 原生客户端无浏览器 CSRF；sameSite 已够 | 无 CSRF |
| 多端 | 网页与 App 共用会话 | 可分开策略 |
| 上架/审查 | 无影响 | 无影响 |

**建议**：**A 先做**，因为不改后端、当天可联调；B 作为后续 ADR（尤其如果要做“注销全部设备”、短会话、或多客户端）。若选 B，必须在 M0 开工前定，否则客户端网络层要重写。
**已记录**：[ADR-0001](adr/0001-session-cookie.md) 已按方案 A 接受；如需改为 B，请新开 ADR 并覆盖该结论。

**需要谁拍板**：后端 + 客户端。
**影响**：`commons/net` 认证实现、后端契约、M0 工期。

## Q6 🟠 API 12 / ArkTS 严格模式边界

**事实**：HarmonyOS NEXT 的 ArkTS 是 TypeScript 的**严格子集**，不是可选项——没有“关闭严格模式跑 TS”的开关。真正要决定的是：

1. 是否 100% 按 ArkTS 约束写（推荐）；
2. 是否为了复用 Web 代码/第三方库引入 JS/WebView（不推荐，Cookie/权限/隐私都不可控）；
3. 是否使用状态管理 V2、API 15+ 新特性（会增加兼容分支）。

**选项**

| 方案 | 说明 |
|---|---|
| A. 锁 API 12 + 全严格 ArkTS（推荐） | 覆盖 HarmonyOS NEXT 5.0.0；`@kit.*` 稳定；不用 API 26 的 `enableAutoCookie` |
| B. 追 API 14/15 | 新特性/新机型；但增加兼容分支 |
| C. 同时兼容 API 11 | 更广；但部分 Kit/权限 API 不可用 |
| D. 混合 JS/WebView | 复用 Web 代码；但破坏“零三方/会话/隐私”边界，不建议 |

**建议**：A。`compileSdk/compatibleSdk/targetSdk = 12`；不使用 `@ObservedV2/@Trace`、`enableAutoCookie`、API 15+ 网络选项；不使用 WebView 承载业务页面。
**影响**：可用 API、测试机型、未来升级成本、可复用的 Web 代码量。

## Q7 🟠 本人修改密码 + 注销全部会话

**现状**

- 只有 `POST /family/members/:id/password`（仅家长，管理员重置）。
- 重置只改 `password_hash`，**不删除 sessions**；旧设备仍有效。
- 没有“注销全部设备”。

**选项**

| 方案 | 需要 |
|---|---|
| A. 维持现状 + 文案提示（推荐短期） | 无后端改动；提示“旧设备可能仍登录” |
| B. 新增 `POST /auth/password` | 旧密码 + 新密码；儿童也可自助 |
| C. 新增 `POST /auth/logout-all` | 删除该用户所有 sessions；重置密码时可选调用 |

**建议**：M3 前做 B/C（如果上架/安全要求）；否则 A + 明确提示。
**影响**：账号安全、上架合规、后端工作量。

## Q8 🟠 数据保留期与用户删除入口

**现状**

- 会话 30 天；录音/评测/聊天无自动过期（以实际代码为准）。
- 有运维脚本 `cleanup-user-data.mjs`（按账号+时间点，删前备份），**不是 App 功能**。
- App 内没有“删除我的数据/账号”。

**选项**

1. 产品提供“联系家长/管理员删除”流程（推荐短期）。
2. 后端新增 `DELETE /me/data`（按时间范围/全部），家长可代孩子执行。
3. 自动保留期（如录音 90 天），后台清理。

**建议**：上架前至少做 1；有精力做 2。
**影响**：合规、存储体积、家长信任。

## Q9 🟠 域名/证书/内网可达性

**现状**

- `https://english.dreamsearch.top` 只在家庭网络/VPN 内可达。
- 依赖家庭 DNS/反代/Caddy 证书。

**需确认**

- 家庭 Wi-Fi 下域名解析到 NAS 的方式（split DNS / hosts / 路由器 DNS）。
- 证书是否被系统信任（Let's Encrypt / 自签）。
- 换路由器/换 IP 后如何恢复。
- 是否允许 VPN/内网穿透（安全风险）。

**建议**：M0 前写一页“家庭网络配置说明”；App 内错误文案区分“DNS 解析失败/连接失败/证书错误”（能区分的前提下）。
**影响**：登录成功率、支持成本。

## Q10 🟡 儿童低分展示策略

**现状**

- 服务端返回完整分数（儿童只剥 IPA，不隐藏低分）。
- 需求要求“孩子不显示低分”。

**选项**

| 方案 | 说明 |
|---|---|
| A. 客户端隐藏 <60 数字（推荐） | 显示鼓励语 + 星星；60+ 显示数字 |
| B. 隐藏所有数字，只显示表情 | 更温和；但家长/孩子看不到进步 |
| C. 服务端返回儿童专用分档 | 需要后端改；客户端更简单 |

**建议**：A；在 `ChildModeFrame`/`ScoreRing` 统一实现，禁止各页面自己判断。
**影响**：儿童体验、家长对“进步”的感知。

## Q11 🟡 音色选择开放程度

**现状**

- `/api/tts` 接受 `voice` 字符串；`/settings` 可存 `tts_voice`。
- 不同 provider 的 voice id 不同；儿童可能误选。

**选项**

1. 只给“默认音色 + 慢速/正常”（推荐）。
2. 给 2–3 个预设（男声/女声/童声），映射到当前 provider。
3. 开放自由输入（仅成人高级设置）。

**建议**：1 首发；2 作为 M1 增强；3 不放儿童。
**影响**：设置页复杂度、TTS 失败率。
